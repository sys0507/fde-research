# Development requirements and independent handoff

Use when the user requests preparation for later development. A developer must understand and implement the agreed product without the conversation or temporary course folders. This stage requires neither source code nor runtime captures; its status is `handoff_ready`.

## Project and materials

Use the requested project. Otherwise select a clear independent location that does not conflict with existing work, such as `projects/<project>/`, with future code in `development/`. A new case starts independently; old products are authorized references, not unexplained inherited code or business conditions.

```text
README.md                         current stage and entry
project-introduction.md           business, roles, product goal, value
functional-development-requirements.md
development-handoff.md            reading order, scope, full task prompt
source-materials/                 necessary originals and existing scenarios
teaching-supplements/             authorized fictional conditions and records
scenario-data/                    seed mappings, branches, coverage
  acceptance/                     expected results, separate from normal inputs
design/                          page responsibilities and visual decisions
development/                     future source; no premature completion claim
```

Copy the complete necessary business package, scenario text/images, and dependencies while preserving original contents/structure. Summaries or chat references alone are insufficient. Check critical paths work within the handoff. Preserve historical links/instructions as source context while stating current development priority. UI references, old lectures, and acceptance answers must not enter the application's business knowledge base.

## Teaching additions need actual content

With authorization, identify missing useful work: normal processing, daily common tasks, cross-role coordination, changes, and recovery. Explain each added/enhanced function and why it belongs; do not expand into an unrelated ERP.

Save `teaching-supplements-and-conditions.md` with addition, original gap, design basis, fictional provider role, date, branch, specific confirmation, supporting attachments, remaining unknowns, and affected functions. Actually create needed sample data/interfaces, role records, resources, receipts, or update records. Label the material fictional; its confirmed state applies to that branch, never the original history.

Separate business permission, technical interface availability, and runtime simulation. Teaching conditions enable full demonstrations without requiring production access. Establish a usable starting point, not pre-completed tasks.

## Implementable requirements

1. **Product/boundary:** roles, objects, first-version scope, capability modes, endpoint, exclusions. Separate business depth from simulation limits.
2. **Coverage:** keep upstream IDs; explain/number additions. Map every requested scene to page, input, action, result, handoff, and acceptance. Representative scenes do not substitute for requested full coverage.
3. **Page/role contract:** responsibility, primary information, entry, controls, visibility/actions, empty/failure/recovery states. Role switching does not change facts; demo controls do not dominate normal work.
4. **Capability division:** ordinary queries/validation/calculation, AI interpretation/extraction/advice, human decisions, approved actions, and condition-triggered automation. Make state, evidence, withdrawal, and failure observable.
5. **Data/rules:** identifiers, relationships, fields, versions, states, events, definitions, cutoff, storage/reset. Lists/details share state; critical amounts are not generated by AI.
6. **Operation contract:** fields/constraints, prerequisites, successful output, side effects, repeat submission, preserved failure contents, and recovery. Explain module cooperation, not just API names.
7. **Seeds/responses:** locate current facts, added conditions, future events, and expected results separately. Responses vary appropriately by object/version/input and cite evidence; no fixed answer for arbitrary questions.
8. **Verification/runtime:** stack rationale, configuration, source location, per-scene steps/results, critical combinations, persistence/reset, captures, and instructions. No runtime means no passed acceptance.

Give concrete inputs/expectations for normal completion, material exception recovery, and condition/version changes where relevant. Do not prescribe a universal scenario count. Acceptance targets data/business outcomes, not titles or button counts.

## Handoff to a developer

`development-handoff.md` is a short entry linking full documents. State objective, allowed write area, input priority/reading order, technical/visual decisions, full coverage, teaching conditions, unresolved decisions, and evidence to return.

Provide a ready-to-use task prompt: read originals/requirements/seed mappings; implement all current scope in the designated write area; model state and capability responsibilities before pages; actually run and check every scenario and critical combination; return code, startup, coverage, captures, and findings. For an existing application say “iterate,” not “start from scratch.” If multi-agent work is separately authorized, assign disjoint modules and shared-interface ownership so teams do not maintain competing state; preserve others' edits.

## Completion

Check readable complete inputs, no omitted functions, implementable endpoints, consistent pages/state/data, sourced or explicit fictional conditions, and no false enterprise approval. Report `handoff_ready`, locations, scope, and work still to develop. Implementation/runtime acceptance have not happened.

Bring concrete alternatives for user decisions. Do not re-request existing teaching-addition authority. If only handoff was requested, stop here; implementation/delegation follows only actual authorization.

Keep one current baseline and reading order. Update the entry with rework, visual choices, rules, and scope changes; label old plans historical. README, handoff, and developer prompt must agree. Track requirements readiness, implementation, runtime verification, and user acceptance separately.
