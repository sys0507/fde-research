# Data, state, and simulation

## Separate originals, seeds, and runtime records

Originals establish existing facts. Seeds extract object IDs, quantities/amounts, versions, cutoff, sources, and permitted teaching additions. Runtime records store prototype actions and never rewrite history as if those actions appeared in originals.

Choose local storage, memory plus export, or a small database according to the task. Related pages must see current changes. Actually test refresh persistence if claimed. Document storage, refresh, and reset behavior. Reset restores demo seeds without deleting originals or other projects.

Distinguish **continuing current state**, where the next role consumes the preceding version/record, from an **independent exercise branch**, which explicitly loads another starting condition. Do not join incompatible branches into one history, preset pending decisions as approved, or abandon useful current-condition organization, checking, calculation, drafts, and handoffs just because final execution is unavailable.

## Simulation choices

| Capability | What actually runs | Boundary |
|---|---|---|
| Query/filter/sort | Results from current local data | Seed data, not live enterprise data |
| Calculation/comparison | Current inputs, explicit formulas, traceable details | Assumptions identified; no invented predictive accuracy |
| AI understanding/answering | Reproducible responses and sources for declared inputs | Identify prerecorded/rule-based behavior; honest unsupported-input response |
| Save/edit/submit | Readable local records, versions, states | Local submission does not mean enterprise receipt |
| External action | Authorized connection or local simulated receipt | Simulated payment/purchase/notice is not real evidence |
| Roles/approval | Role-specific local behavior/flow | Demo switching is not authentication/backend enforcement |

For explicitly requested real models, inspect the environment, processing constraints, service, and official interface/code. Read credentials from protected configuration. If unavailable, report it; never silently substitute simulation and claim a real call. Otherwise do not request API keys unnecessarily.

## Results and failure

Save creates a record; evidence opens relevant material; submission leaves receiving state/tasks. Corrections to reviewed/approved/audited records preserve relevant old versions/reasons. Extra versioning or reasons for ordinary unsubmitted drafts depend on requirements; the general skill does not add mandatory fields/approvals. Offer correction/back/continue as appropriate; not every action must be irreversible.

Important failures should be demonstrable: required data blocks submission with a specific explanation; absent sources limit an answer; old versions require review. Explain next steps. Avoid random failure and loading animations as a substitute for behavior.

Check source-matching amounts, quantities, times, and states. Verify derived totals through actual computation, not by trusting displayed values. Distinguish query, recommendation, approval, and execution.

## Shared state and combined operations

Lists, details, dashboard numbers, tasks, and roles read one current state, not independent initial JSON. Role switching changes visibility/actions without resetting objects or consuming events. Only explicit exercise switching replaces seeds.

Current version, approved version, reserved quantities, and remaining balances come from traceable records. Ordinary program rules handle transitions and arithmetic; AI text does not directly alter ledgers, permissions, or execution status. Repeat clicks, refresh, and subsequent edits must not duplicate inventory, receipts, payments, or consume the same balance twice.

Check relevant combinations, such as changing an approved version before execution or changing settlement after a replenishment commitment. Recheck applicable conditions instead of subtracting independently from original balances. Define unchanged state on rejection, draft retention, and partial completion/recovery. A prototype need not implement production transactions, but must enforce business invariants within scope.

## Business evidence versus development references

Organize retrievable originals, fictional business additions, UI images, scenario descriptions, and expected answers separately. Screenshots, lecture notes, and acceptance answers are not business attachments or retrieval knowledge. Copying a material into the project does not authorize exposing it in the frontend/model context.

## Role actions and automation recovery

Define view, edit, save, send, receive, take ownership, confirm, approve, and execute separately. Viewing evidence/pages or switching roles creates no business approval/execution event. Technical access logs are permissible without advancing work. Separate shared facts from private role drafts; switching identity does not publish private content or sign another person's opinion.

When rules, sources, or versions change, mark affected advice, approvals, and execution readiness, retaining old bases. An unchanged amount does not prove approval remains valid.

For multistep automation show current authority, completed/pending steps, failure, and receiving role. Keep successful work and resume only unfinished actions; repeated triggers must not duplicate notifications, orders, stock, or money. If automation is outside scope, demonstrate the endpoint through real local human-confirmed steps without invented approval.
