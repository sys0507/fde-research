# Verification and delivery

## Verify work results

Exercise each contract scenario and distinguish tested/untested. Check input affects output, results persist, later roles/pages consume the same state, and important errors recover. HTTP 200, clickable buttons, and headings alone are insufficient.

Deterministic seeds enable repetition. Check normal paths, decisive state boundaries, and known defects. Use focused tests for material calculations/state rules and real browser checks for main behavior; do not test every style or repeat equivalent audits.

Actually start the service or open the standalone page. Record command, working directory, port, dependencies, port-conflict handling, and whether the service remains running. Choose another free port instead of stopping unrelated projects. Without a browser, do not claim visual/click acceptance; hand off unverified items and reproducible steps.

## Screenshots and visual checks

Capture the new running prototype after actual operations. Record function/scenario ID, page/route, object, cutoff, action, image, and simulation status. Prefer images showing meaningful tasks/results; multiple scenarios may share one readable state instead of requiring three new images each.

Qualified original-workflow captures from scenario design may be reused for comparison, clearly distinguished from new runtime screenshots. A screenshot gallery, unimplemented mockup, or pictured button is not product interaction.

Inspect representative pages and discovered layout issues for identity, object, fields, state, sources, and controls. Check desktop and needed narrow layouts/navigation/forms/error feedback; a desktop demo does not automatically require a production mobile system.

## Sufficient delivery package

One README should locate:

- Runnable source, dependencies, local data/assets, appropriate lockfiles and configuration examples without credentials.
- Startup, actual entry, roles, main tasks, save/refresh, reset, shutdown, and remaining external dependencies. Do not promise installation-free portability.
- Function/scenario coverage with upstream IDs, entries/actions, actual results, and missing/partial work.
- Real verification records/captures and simulated-versus-real capability inventory; no invented operations.
- Requirement findings with affected scenarios, proposed changes, basis, responsible decision roles/conditions, and current treatment; state if none.

Maintain a short image index for downstream reports:

| Function/scenario | Relative image | Action/result | Version and simulation basis | Supported conclusion | Still pending |
|---|---|---|---|---|---|
| Existing ID | Capture path | Actually observed behavior | Prototype/seed version | How the role can work | Interfaces, authority, or rules |

Reports may reuse evidence but do not have to wait for a prototype. Development speed, click-through success, or fixed answers prove neither production savings nor model accuracy/live integration.

## Completion and continuation

Report agreed scope and actual verification coverage. Missing core functions, startup failure, or untested main actions mean partial completion with a concrete next step; generated code alone is insufficient.

Finish a requested partial prototype when that scope passes; do not expand automatically. A full-scope request cannot be satisfied by representative pages only. Update affected scenarios, states, and materials on feedback instead of rebuilding working parts. Default delivery is local; do not automatically publish, connect real systems, or send to stakeholders.
